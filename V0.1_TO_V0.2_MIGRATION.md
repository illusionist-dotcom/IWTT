# MIGRATING v0.1 → v0.2

**Short version: opening your v0.1 vault with v0.2 migrates it in place, changes no
canonical row, and can be undone by deleting the derived layer.**

Tested by `tests/test_migration_v01_to_v02.py` (7 tests) against a byte-faithful
v0.1-format database, and end-to-end by `scripts/verify_release_v02.py`
(`migrationFromV01` — result **PASS**).

---

## 1. What migration does

`Vault.__init__` calls `initialize()`, which is the only migration path. On a v0.1
file it:

1. sets `PRAGMA journal_mode = WAL` (as v0.1 did);
2. runs v0.1's `SCHEMA_SQL` — pure idempotent `CREATE … IF NOT EXISTS`, so an
   existing v0.1 file is untouched;
3. runs v0.2's `RECALL_SCHEMA_SQL`, creating nine **derived** `recall_*` tables plus
   their indexes;
4. inside one explicit `BEGIN IMMEDIATE` transaction, writes version markers to
   `schema_info`, recording `migrated_from_app_version` and `migrated_at` **only** on
   the first v0.2 open of an existing v0.1 vault.

Both DDL scripts run *before* the explicit transaction on purpose:
`sqlite3.executescript()` issues an implicit `COMMIT`, which would otherwise silently
end the transaction the version markers are written in. If anything fails, the
transaction rolls back and the vault is exactly as it was found.

**That is the whole migration.** Nothing is rewritten, reindexed in place, or
re-identified. The derived indexes are built lazily on first use
(`RecallIndex.ensure_fresh()`) or explicitly with
`vault.rebuild_recall_indexes(full=True)`.

## 2. What does *not* change

| | v0.1 | v0.2 |
| --- | --- | --- |
| `schema_info.schema_version` | `'1'` | **`'1'` — unchanged** |
| Canonical tables | `thoughts`, `revisions`, `tags`, `thought_tags`, `relationships`, `events`, `schema_info` | **identical, no new tables, no new columns** |
| Thought ids | UUIDv4 | **the same UUIDv4s** |
| `original_text` | immutable via `BEFORE UPDATE` trigger | **still immutable, trigger untouched** |
| Revisions / events | append-only history | **identical rows** |
| Relationship provenance | `USER_CONFIRMED` / `AI_SUGGESTED` × `SUGGESTED` / `CONFIRMED` / `REMOVED` | **identical model, not weakened** |
| Export format | `iwtt-vault-export`, `schemaVersion: 1` | **identical** — a v0.1 export imports into v0.2 unchanged, and a v0.2 export imports into v0.1 |
| `search_documents`, `derived_artifacts` | v0.1's derived tables | **still there, still v0.1's** |
| `Vault.search()` | v0.1 lexical search | **byte-identical behaviour** (`tests/test_store.py`, 15 tests, frozen) |
| HTTP routes | v0.1 routes | **all unchanged**; v0.2 adds new ones |
| Dependencies | standard library only | **standard library only** |

The canonical export schema version is deliberately **still 1**. v0.2 adds derived
intelligence, not canonical meaning, so a v0.1 reader must be able to read a v0.2
export and lose nothing but the derived layer it never understood.

New `schema_info` rows (additive only):

| Key | Value after migration |
| --- | --- |
| `schema_version` | `1` |
| `recall_schema_version` | `3` |
| `app_version` | `0.2.0` |
| `migrated_from_app_version` | `0.1.x` |
| `migrated_at` | UTC ISO-8601 |

`vault.schema_versions()` reports these in camelCase for API consumers;
`vault.schema_info_rows()` returns the literal rows exactly as stored, for auditing.

## 3. Back up first

Migration is additive and reversible, but take a backup anyway — it costs one call:

```python
from iwtt.store import Vault
vault = Vault()                 # ~/.iwtt/thought-vault.sqlite3 by default
print(vault.backup())           # -> path under <data-dir>/backups/
```

or through the API:

```
POST /api/data/backup
```

Backups are file-level SQLite copies named `iwtt-backup-<UTC timestamp>.sqlite3` in
`<data-dir>/backups/`. `scripts/verify_release.py` asserts every backup passes
`PRAGMA integrity_check`. You can also copy the file yourself while IWTT is not
running — a single SQLite file, no sidecars, nothing else to find.

---

## 4. Rolling back

Rollback is not a special mode; it is **deleting the derived layer**, because v0.1
never reads those tables.

**Preferred — through the API or Python:**

```python
vault.clear_derived_data()              # or: DELETE /api/data/derived
vault.delete_all_derived_intelligence() # v0.2's derived layer only
```

**Complete — back to a file v0.1 opens as its own:**

```sql
DROP TABLE IF EXISTS recall_tokens;
DROP TABLE IF EXISTS recall_trigrams;
DROP TABLE IF EXISTS recall_docs;
DROP TABLE IF EXISTS recall_graph_cache;
DROP TABLE IF EXISTS recall_clusters;
DROP TABLE IF EXISTS recall_query_memory;
DROP TABLE IF EXISTS recall_term_stats;
DROP TABLE IF EXISTS recall_meta;
DROP TABLE IF EXISTS recall_build_log;
DELETE FROM schema_info
 WHERE key IN ('recall_schema_version','migrated_from_app_version','migrated_at','app_version');
```

Then run the v0.1 build against the file. `test_rollback_leaves_a_file_v01_can_still_open`
asserts that after this: `schema_version` is still `'1'`, no `recall_*` table remains,
`search_documents` and `thoughts` are still there, `PRAGMA integrity_check` is `ok`,
every canonical row is byte-identical to the pre-migration snapshot, the canonical
fingerprint is unchanged, and v0.1-style `search("enemy adapting player")` still
returns results.

**What rollback costs you:** derived recall indexes, clusters, graph caches and
query-outcome memory. All of it is rebuildable. **What it never costs you:** a
thought, an original text, a revision, an event, a tag, a relationship, a provenance,
a lifecycle state, or a Graveyard/resurrection timestamp.

## 6. The destructive guarantee

Migration is the easy half. The half that matters is that **canonical memory survives
the complete deletion of every derived artefact v0.2 creates** — proven by
`tests/test_canonical_destruction.py` and by `verify_release_v02.py`:

```
derivedDeletion:
  canonicalTablesTouched:  []
  recallTablesDeleted:     9
  recallRowsDeleted:       545
derivedTablesAfterDeletion: every recall_* table = 0 rows
canonicalFingerprintPreserved:  true
canonicalRowsByteIdentical:     true
recallAfterRebuild:
  sameRankingAsBeforeDeletion:  true      # rebuild reproduces the identical order
  topResult:                    true
```

`canonical_fingerprint()` hashes the canonical projections; equality before and after
deletion is the check, not a claim.

## 7. If something goes wrong

1. **Do not hand-edit `thoughts`.** The `BEFORE UPDATE` trigger will refuse an
   `original_text` change, and that refusal is a feature.
2. Restore the backup file over `~/.iwtt/thought-vault.sqlite3` (or your
   `IWTT_DATA_DIR` / `--data-dir` location) while IWTT is not running.
3. If recall behaves oddly but the vault is fine, delete the derived layer
   (§4) and let it rebuild: `POST /api/recall/index/rebuild`, or
   `vault.rebuild_recall_indexes(full=True)`.
4. `GET /api/recall/index` reports index state and drift (`stale`,
   `signatureMatches`, `schemaCurrent`, `canonicalThoughts` vs `indexedDocuments`),
   which is the first place to look.
5. Report the output of `python3 scripts/verify_release.py` and
   `python3 scripts/verify_release_v02.py` — both print PASS/FAIL with the evidence.

## 8. Version markers

| | v0.1 | v0.2 |
| --- | --- | --- |
| `APP_VERSION` | `0.1.0` | `0.2.0` |
| `CANONICAL_SCHEMA_VERSION` | `1` | **`1`** |
| `RECALL_INDEX_SCHEMA` | — | `3` |
| `EXPORT_FORMAT` / `EXPORT_SCHEMA_VERSION` | `iwtt-vault-export` / `1` | **unchanged** |

A `recall_schema_version` mismatch never triggers a partial upgrade: the derived
layer is rebuilt from scratch. Derived data has no migration history because it has
no authority — that is the point of keeping it derived.
