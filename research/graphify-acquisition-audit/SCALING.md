# SCALING.md

**Audit 8 — Scale.** Storage technology, memory behaviour, index strategy,
incremental behaviour, and measured performance from 1,000 to 1,000,000 nodes.

The mission brief says: *Do not fabricate benchmarks. If measurements are
unavailable, label conclusions ESTIMATED.* Everything below is either **MEASURED**
(in this audit's sandbox, on synthetic corpora) or explicitly **ESTIMATED** with
the arithmetic shown.

---

## 1. Storage and representation

| Aspect | Implementation | Evidence |
|---|---|---|
| Graph library | NetworkX (`networkx>=3.4`) | `pyproject.toml`; `build.py`, `cluster.py`, `serve.py` |
| Persistence format | One JSON document, `graphify-out/graph.json`, NetworkX node-link form | `export.py::to_json()`, `paths.py::load_node_link_graph()` |
| Write strategy | **Whole-file rewrite** per build, with a shrink/loss guard | `to_json()` pre-write block |
| Read strategy | Whole file into memory, then whole graph into NetworkX | `serve.py::_read_graph()`, `_load_graph()` |
| Server residency | Bounded cache of loaded graphs | `_GraphContextCache`, `_max_server_contexts()` |
| Indexes | None persisted. Two in-memory, lazily built, cached **on the graph object**: `_idf_cache`, `_trigram_index` | `serve.py` |
| Per-file cache | Content-hash keyed AST cache, namespaced by package version + cache schema + grammar fingerprint | `cache.py::_AST_CACHE_SCHEMA = 16`, `cache_dir()` |
| Semantic cache | Content-hash keyed, deliberately *not* version-invalidated | `cache.py::check_semantic_cache()` |
| Change detection | mtime/size stat signature before hashing | `cache.py::_stat_sig_fresh()` |
| Parallelism | `ProcessPoolExecutor` above `_PARALLEL_THRESHOLD = 20` uncached files; workers default to `cpu_count` / `GRAPHIFY_MAX_WORKERS` | `extract.py` |
| Incremental | Watch mode + incremental extract with `resolution_context_*`; **clustering, analysis, report and `graph.json` are always rebuilt whole** | `watch.py`, `extract.py`, `cli.py` |
| Read guard | Graph file size cap | `security.py::check_graph_file_size_cap()` |

**Implication:** there is no database. The design is "one JSON file + NetworkX in
RAM, fully rewritten each build." That is *excellent* for a single-user local
system (simple, inspectable, diffable, no server) and it is the design's hard
scaling ceiling.

### 3.3 Query-stage breakdown (where retrieval time goes)

| Nodes | Score | Seeds | BFS | Render | **Total** | `_path_search_graph` |
|---|---|---|---|---|---|---|
| 1,000 | 12 ms | 0.1 ms | 6 ms | 15 ms | 33 ms | 19 ms |
| 10,000 | 72 ms | 0.0 ms | 15 ms | 9 ms | 96 ms | 188 ms |
| 100,000 | 792 ms | 0.1 ms | 154 ms | 28 ms | 973 ms | 1,998 ms |
| 250,000 | 2,393 ms | 0.1 ms | 406 ms | 37 ms | 2,836 ms | 5,304 ms |

All MEASURED. Two things stand out:

1. **Scoring dominates.** The lexical pass over candidate nodes is 80–85% of query
   time, and it grows linearly with graph size — the trigram prefilter's
   whole-graph fallback guard (fires when a term's rarest trigram covers >10% of
   nodes) is triggered at these sizes, so scoring is effectively a full scan.
2. **Path search is the expensive operation.** `_path_search_graph` builds a
   traversal copy of the graph per call: 2.0 s at 100k, 5.3 s at 250k. Graphify's
   own tool docs steer agents to `query_graph` for breadth and `shortest_path` for
   a specific trace; the cost model justifies that guidance.

## 5. Measured failure at 500k / 1M on the file-load path

The in-process path (§3) constructs the graph from a Python dict, so it never
holds the JSON text. The **normal product path** reads `graph.json` from disk.
Measured separately, from pre-built files, under a memory cap so the failure mode
is a clean `MemoryError` rather than an OOM kill:

| File | Nodes | Read as text | `json.loads` |
|---|---|---|---|
| `corpus_500k.json` (233 MB) | 500,000 | 0.43 s, peak RSS **477 MB** | **MemoryError** at peak RSS 1,617 MB (cap 1,800 MB) |
| `corpus_1m.json` (469 MB) | 1,000,000 | 0.67 s, peak RSS **926 MB** | **MemoryError** at peak RSS 1,587 MB |

All MEASURED. Reading the file as a Python string costs ≈ **2.0×** the file size;
`json.loads` then needs several times more, and `node_link_graph()` adds the
NetworkX object on top. Separately, generating the 500k and 1M corpora in-process
was **OOM-killed (exit 137)** on this ~1.9 GB machine, before graphify was reached.

**ESTIMATED arithmetic for a normal machine** (extrapolating the observed ratios,
clearly labelled as an estimate):

| Size | file | read text | parsed dict | NetworkX graph | **Estimated peak** |
|---|---|---|---|---|---|
| 500k | 233 MB | ~0.5 GB | ~1.2–1.6 GB | ~1.0–1.5 GB | **~2.5–3.5 GB** |
| 1M | 469 MB | ~0.9 GB | ~2.5–3.5 GB | ~2.0–3.0 GB | **~5–6 GB** |

**Conclusion (ESTIMATED):** the 1M-node case is reachable on a 16 GB machine but
is not ergonomic — minutes per rebuild, seconds per query, gigabytes resident, and
a whole-file JSON rewrite on every build. For IWTT, 1M is far beyond any plausible
decade of personal thought capture; 10k–100k is the realistic band, where this
architecture is genuinely comfortable.

## 6. Honest summary for IWTT

**Strengths at IWTT scale:**
- No database, no server, no daemon required — a folder of files.
- Whole-file JSON is inspectable, diffable, backup-friendly, and trivially
  mirrored into a user's existing sync/backup strategy.
- 10k thoughts: sub-100 ms retrieval, ~3 s full rebuild. Better than interactive.
- Rebuild-only clustering is the right trade at this scale: no incremental
  clustering complexity, deterministic results, stable ids.
- Memory footprint is modest (~1 KB per node).

**Ceilings to design around:**
- Whole-file rewrite per build means every build touches every byte; on
  synced/networked storage that is a real cost well before CPU is.
- No persisted index: every server start rebuilds the trigram index (0.1 s at 1k,
  ~10 s at 100k, ~25 s at 250k). Acceptable, but it is startup latency.
- Query cost is linear in graph size whenever the trigram guard trips.
- `shortest_path` copies the graph per call.
- One JSON document is a single point of corruption (mitigated by the shrink
  guard and atomic writes, not by redundancy).

**Design recommendations that follow (for a later mission):**
1. Keep canonical thoughts in a store that does **not** require rewriting
   everything to change one record (append-only log, or per-thought files) — do not
   copy Graphify's single-JSON-document shape for canonical data.
2. Do copy Graphify's *rebuildable projection* pattern: a `graph.json`-style
   derived snapshot is a fine artifact as long as it is disposable.
3. Persist the derived indexes (trigram, IDF) alongside the derived snapshot if
   startup latency ever becomes visible; they are rebuildable by definition.
4. Keep algorithm outputs (clusters, scores) in sidecars with a generator version,
   so a rebuild is a pure function of canonical state + algorithm version.

## 7. What Graphify's own benchmarks claim at scale

`BENCHMARKS.md` reports a temporal suite of **689 weekly AST checkpoints,
2011 → 2026**, growing from 3,069 nodes / 2,900 edges / 1,032 files (2011) to
22,620 nodes / 48,710 edges / 3,758 files (2026) — about 7× nodes, 17× edges across
15 years of a large production codebase, built deterministically with no LLM.

That is a **vendor claim and was not reproduced** (the harness is not published).
It is nonetheless the most relevant scale datapoint available for IWTT: a large
real-world corpus spanning 15 years sits comfortably in the 3k–23k node band. A
personal thought vault that reaches 10k nodes is, by this comparison, already a
substantial long-lived corpus.
